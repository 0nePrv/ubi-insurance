# ADR-0002: Event sourcing только для агрегата Policy

**Status:** Accepted
**Date:** 2026-09-11

## Context

Полис живёт годами и меняется посреди срока. При убытке ключевой вопрос — «что покрывал полис на дату ДТП»,
в том числе с учётом изменений, внесённых задним числом. Остальные агрегаты таких требований не имеют.

## Decision

- Policy хранится как поток событий в Postgres (`policy_events`), optimistic concurrency через `unique (stream_id, version)`.
- Две временные оси: `effective_at` (бизнес-время) и `recorded_at` (системное время) — битемпоральность.
- Внутренние события (jsonb) отделены от интеграционных (protobuf в `contracts`).
- Публикация в Kafka — через отдельный outbox, а не чтением event store по `global_position`
  (sequence выдаётся до коммита, возможен пропуск событий при конкурентных транзакциях).
- Claim — конечный автомат на JPA с таблицей истории; Billing — append-only леджер; Quote — Redis.
- Самописный event store вместо Axon/EventStoreDB: механика важнее фреймворка, и её нужно уметь объяснить.

## Consequences

- Легче: запросы «на дату», аудит, объяснение истории премии (`proposed` vs `applied`).
- Сложнее: проекции для чтения (CQRS), эволюция схемы событий (upcasting), снапшоты при длинной истории.
- Пересмотреть: снапшоты — когда поток одного полиса превысит сотни событий.
